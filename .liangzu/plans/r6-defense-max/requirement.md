# R6 冻结需求 —— freedom 加密产物与防御能力最大化

## 用户目标（原话）

> 继续对freedom的加密产物和防御能力进行最大化的提升

## 本轮取证出的真实缺陷（需求由此重排）

对抗边界不是"逆向壳"，而是 **npm 包自己就把万能钥匙发出去了**：

- `freedom-cli/lib/security.js:32` 内置全域 `MASTER_KEY_CIPHER` + 掩码算法；
- 同文件 `:160 decryptApp()` / `:181 buildIntegrity()` 是可直接调用的解密器与清单生成器；
- 容器派生钥 = `PBKDF2(master, DERIVE_SALT:应用名 + 容器自带盐)`，其中「应用名」就是 exe 文件名、
  「容器自带盐」在 `app.bin` 头 16B 里——**两者都在产物自己身上**。

⇒ 任何 `npm i @yufengtadian/freedom-cli` 的人，无需调试、无需逆向，即可离线解密任意 high 产物，
并为自己改造的内容生成合法 `.integrity`，让壳照跑（端到端已实测，见 findings）。

## 架构约束（决定方案空间）

通用预编译壳 = 零工具链打包路径：**没有构建期编译步骤**，因此任何"每产物专属秘密"都只能来自产物文件本身；
运行期能用于解密的密钥，攻击者拿到产物即拿到。对称加密在这条路径上只能给到混淆级强度，
这是设计事实不是实现缺陷。能真正引入非对称强度的是**发布方私钥**（`freedom keygen` 已在 `.freedom/keys/`，
从不进产物）。

## 验收（逐字抄进 progress 的判据列）

- A1 红→绿：现有 PoC 两件事必须在加固后的产物上失败——① 仅用公开 CLI 离线解密产物；② 自造清单换后端后壳仍启动。
      ①须报"缺 per-product 密钥不可解密"，②须启动即拒（退出码非零、零窗口、零明文残留）。
- A2 跨语言同步：Go `security.go` 与 CLI `lib/security.js` 双侧改齐，黄金向量更新；
      旧 FRDM2 容器在新壳上必须明确拒绝（不静默降级），保留既有"旧容器拒绝"用例的语义。
- A3 真机：win-x64 high 产物正常启动跑通；篡改 / 伪造 / 改名三类用例全部拒跑且无临时目录残留。
- A4 文档口径：README / SECURITY / CHANGELOG 对"通用预编译壳（零工具链）"与"自编译壳"两档强度如实分层描述，
      不再出现无条件"逆向不出来源码"表述。
- A5 全闸门：`node --test tests/*.test.mjs`、`go test -count=1 ./...`、gofmt、模板镜像比对 exit=0。

## 不做什么（防范围膨胀）

不引入 KMS/HSM/服务端下发（产品要离线运行）；不做白盒 AES（Go 侧无成熟实现，体积与维护代价失衡）；
不做前端 JS 混淆（不解决本波任何缺陷，只加重误报）；不改 FRDM2 的 AES-256-CTR + Encrypt-then-MAC 算法本体
（它不是本波短板，被绕过的是密钥模型不是算法）。
