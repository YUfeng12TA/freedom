# R6 方向闸门 —— 加密与防御最大化（S3，三方向对比后再动手）

> 输入是本轮实测（见 `r6-defense-max/findings.md`）：对抗边界已从"逆向壳"塌缩到"读 npm 包"。
> 故本波不是"把 AES 调得更狠"，而是**换密钥模型**。

## 方向对比

| 维度 | D1 非对称绑定（清单改签名 + 壳自检） | D2 每产物专属对称钥（自编译线） | D3 运行期防御补全（零落盘 + 反调试补全） |
|---|---|---|---|
| 解决什么 | 伪造/换后端/重放/换壳：无发布方私钥即造不出合法产物 | 破解一个产物≠能解所有产物；npm 包不再自带万能解密器 | 磁盘明文源码消失；动态取密钥成本上升 |
| 挡住本波 PoC？ | ②（自造清单被拒）**能**；①（离线解密）**不能**（钥仍可算） | ①**能**（CLI 不再持有全域 master，改为 per-app key 文件） | 都不能（PoC 根本不需要落盘明文或调试器） |
| 强度来源 | 数学（ed25519，私钥不出发布方） | 秘密分布（每产物一把，存 `.freedom/keys/`） | 赌攻击者不想动态调试 |
| 复用既有资产 | `freedom keygen` 私钥环 + `updater` 的 ed25519 验签与 `RequireSignature` | 现有 `deriveSecurityKey(appName, salt)` 只是把 master 换成 per-app | `securetemp*` / `anti_debug_*` / `shutdown*` 已在 |
| 兼容性 | 需断代（清单 v3；旧壳遇新清单要拒） | 需断代（容器 magic FRDM3；旧 FRDM2 明确拒绝） | 不破格式（可增量） |
| 工作量（粗估） | Go+JS 双侧、清单结构、CLI 签/验、壳启动验签、真机三类用例：~1.5 天 | CLI 生成/保存 key、build 注入、Go 读取路径、黄金向量重生成：~1 天 | macOS 反调试 + 解释型后端 stdin 注入 + 编译型后端前置：~2 天且含真机不确定项 |
| 主要风险 | 用户丢私钥 = 无法再更新产物（需在 `keygen` 提示里写清） | 零工具链用户仍走 Tier A（诚实分层，不当作已解决） | macOS 无真机=不可验证；stdin 注入对 node/python 之外的后端形态受限 |

## 推荐：D1 + D2 同一波（一次断代 FRDM2→FRDM3），D3 独立后续波

理由：
1. D1 是**唯一有非对称强度**的一击，且几乎全部零件已存在（ed25519 密钥环、验签代码、清单文件），
   把 `.integrity` 从"HMAC(公开钥)"改成"sig(privKey, app.bin 摘要 + 应用名 + 容器盐 + 壳自身摘要)"即成；
   壳侧公钥验签 ⇒ **第三方连"伪造一个能跑的产物"都做不到**，这条当前是敞开的。
2. D2 把"npm 装包即万能解密"这条致命路径关掉：master 不再进公开源，改为每产物随机 key 存发布方本地，
   派生链其余不动（最小改动，不做白盒、不换算法）。
3. 两者都要动容器/清单格式与跨语言黄金向量 ⇒ 一次断代比两次便宜，且用户只需重打包一次。
4. D3 单独看性价比最低（PoC 证明它挡不住本波攻击），且 macOS 分支无真机不可验，放后续波。

## 阶梯止于（防过度设计结论）

- 不新建"加密框架/提供者抽象层"：清单仍是那一个 JSON 文件，只加 `sig` 字段与版本位；
- 不为 D2 引入第二套配置项：per-app key 就存 `.freedom/keys/<app>.key`，与既有 `updater.key` 同目录同纪律；
- 不动 AES-CTR+HMAC 算法本体、不动 PBKDF2 迭代数；
- D1/D2 落地后**不顺手做** macOS 反调试（无真机＝不可验，另波）。

## 需要用户裁定（阻塞实施的唯一一项）

FRDM3 断代 = 已发布的 FRDM2 加密产物必须重新打包；且发布版本号按铁律 14 由你指定。
