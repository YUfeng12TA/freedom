# R7 源码保护强度闸门 —— FRDM3 之后还剩什么可抬

冻结日期 2026-09-25。上游：R6（FRDM3 + Tier B，台账 B-20260925-054 已关）。
本档是**方向闸门**（多方案对比 → 推荐 → 阶梯止于），实施账在 `task_plan.md` / `progress.md`，取证在 `findings.md`。

## 0. 目标与边界（复述一句话）

在不动摇 1.14.0 已定的容器/清单契约的前提下，把"从已发布产物里拿到可读源码"的成本从
**「有工具链即可自动化」**抬到**「每个产物都要人工逆向一次，且拿不到就当场跑不起来」**。

非目标：不追求 DRM 意义上的"绝对不出"（§2 论证它在本架构下不可达）；不做需第二调用方才成立的抽象。

## 1. 取证结论：R6 之后仍可拿到明文的四条现实路径（本轮实测核对，逐条 file:line）

R6 关掉的是**离线解密任意产物**与**伪造合法清单**这两条（主密钥出公开源 + 清单改非对称签名）。
以下四条是 R6 未覆盖的残留面，全部在本轮重新 grep 确认仍存在：

1. **派生密钥终生驻留（最高价值缺口）**
   `security.go:603-621 deriveSecurityKeyV3` 把 KEK 与 macKey 写进全局 `secureKeyCache`
   （`security.go:586-597 cacheSecureKey`，上限 `secureKeyCacheMax = 8`，单进程正常只用 1~2 条 ⇒ 淘汰分支实际不触发）。
   ⇒ 攻击者只需**一次内存取样**拿到这 64B，即可对**磁盘上的 `app.bin` 离线全量解密**
   （salt/iv 都在容器头，`decryptAppBinV3` 除 KEK 外无别的秘密输入）。
   这一条把"内存 dump"从"只能看当前明文"升级成了"永久有效的解密能力"——是本波最大 ROI。
2. **明文全量副本 2 份**
   `security.go:373-378` 注释写明刻意不缓存载荷，于是 `resources.go:98 loadRuntimeConfig` 与
   `resources.go:274 loadRuntimeHTML` **各触发一次读盘 + 解密 + json.Unmarshal**
   ⇒ 堆内同时存在两份 html/config/backend 源码明文，且 `security.go:676 plain` 与
   `security.go:490-528` 物化后的 `secureFile.Data` 都**从不 `clearBytes`**
   （对照：`security.go:419 defer clearBytes(master)` 说明这条纪律已有，只是没铺全）。
3. **静态掩码是公开固定式**
   `security.go:578-586 productMaster` 与 `freedom-cli/lib/security.js:91-94 maskPositional` 同式
   （`out[i] ^= (i*7+0x5A)`），而 **npm 包与 GitHub 都带着这个算法**（用户裁定「保持公开」）。
   ⇒ 对能读公开源的人，壳里那串 hex 只是"少写三行脚本"；更糟的是逆向成果**跨产物复用**——
   写一个通用脱壳器，之后所有 Freedom Tier B 产物一次到位。
   （诚实分级：这一条挡不住"人"，只挡住"自动化与复用"。见 §2。）
4. **磁盘面：后端源码在运行期以明文落在临时目录**
   `materializeSecureBackend` 已做到 0700 目录 / 0600 文件 + 退出即删 + 下次启动按 PID GC
   （`security.go:481-528`、`resources.go:260-268`），残留窗口只在"崩溃/强杀到下次启动之间"。
   同 UID 对手在此窗口内可读——但同 UID 本就是桌面平台的信任边界外（§2 第 3 条）。

## 2. 结构性天花板（必须先对齐的期待，否则任何方案都是在卖纸面强度）

1. **对称加密不可能同时做到"壳能自动解开"与"逆向者解不开"**。壳必须在运行时自己拿到明文（webview 要 HTML、
   子进程要可执行文件），所以"逆向不出"在这条路上**不可证**。能抬的只有两项：**成本**（人工逆向工作量）
   与**复用性**（破一个 ≠ 破所有）。
2. **公开源里带着解密算法 ⇒ 算法保密型加固全部无效**（Kerckhoffs 前提已被"保持公开"锁定）。
   唯一还能产生差异的是**每产物唯一的数据/代码**——即 §3 乙的多态装配。
3. **同 UID / 能读进程内存的对手不在防御范围内**：`anti_debug_*` 只是抬高门槛（Windows 七道信号，Linux
   PTRACE_TRACEME），不是边界。真要"对手读不到"，只有把敏感逻辑挪出客户端。
4. ⇒ 若用户要的是**"逆向就是拿不到源码"**这个语义，本框架内不存在实现路径，唯一手段是
   **核心逻辑放服务端**（客户端只持有 RPC 凭据与 UI）。这是架构取舍，不是打包参数，列在 §5 待裁。

## 3. 候选方向（甲 / 乙 / 丙 / 丁）

### 甲 —— 内存明文生命周期收口（不做格式断代）

- 载荷**单次解密**并缓存（`loadSecureResources` 加 load-once 门），两处调用点行为与错误语义不变（仍 `secureFatal`、仍 exit 70）；
- KEK/macKey **不再跨调用缓存**：随解密函数进入即派生、返回即 `clearBytes`；
- `plain` 解密缓冲 `json.Unmarshal` 后立即擦；`secureFile.Data` 物化落盘后逐文件擦。
- 与 1 的冲突及裁决：现有"不缓存载荷"的理由是"容器被替换后立即失效"。缓存之后运行期无人再读 `app.bin`
  ⇒ 换盘变成惰性事件，该属性失去价值；而它换来的代价是 KEK 终生驻留（缺口 1）。
  启动路径上 config 与 html 两道门仍各自校验（缓存的是"已校验通过"这一事实），故 R6 的真机三类用例不变。
- **净收益含提速**：PBKDF2 600k 从每进程 2 次降到 1 次（R6 findings 实测 ~180ms/次）⇒ 启动 −180ms。
- 破产物格式：否。失败模式：无（纯运行期）。

### 乙 —— 每产物多态密钥装配（抬"复用成本"，不抬"绝对强度"）

- CLI 在 Tier B 构建目录（**临时目录，不入库、不发布**）代码生成一份 `keyslot_*.go`：
  主密钥拆成 N 片（每构建随机 N、随机顺序、随机组合式：xor / add / 反序 / 分段错位），
  运行期由生成码装配出 master，替换现在的单变量 `securityMasterCipher` + 固定掩码。
- 锚公钥 `securityAnchorPubHex` 留在 `-X`（它本就不需要保密）。
- 价值锚点：**破解一个产物得到的成果对下一个产物无效**（每个产品的装配片段唯一且不公开），
  这正是 R6 per-product 主密钥在"数据面"做过的事，本方向把它搬到"代码面"。
- 风险与既有防线：装配注入若断链，`productMaster()` 的长度校验会返回 `ok=false` ⇒ 产物**响亮拒跑**，
  不会退化成"用空字节当密钥"（契约 §6.3 警惕的静默空密钥在此有结构兜底）。
- 破产物格式：否（容器与清单不动）。改动面：`lib/build.js`/`lib/security.js` + 生成模板 + `security.go`
  + 镜像同步 + 契约 §6.3 注入符号表与其逐字锁死的 JS 测试。

### 丙 —— 磁盘面收口（后端源码不落明文）：爬梯后判「不做」

阶梯①现有资产：0700/0600 + 退出删 + 下次启动 GC，已把窗口压到崩溃残留。
阶梯②可替代落盘：`node -` / `python -` 走 stdin、Go 编译型后端不需要文件、
Linux `memfd_create`、Windows 无对等原语（管道不能当解释器实参）。
⇒ **止于**：做到"全语言不落盘"必须按解释器分叉后端契约（`examples/multiproc` 四语言即第一道墙），
换来的是**只防同 UID 对手**（§2 第 3 条明确不在防御范围内）。成本 = 契约分叉 + 四语言矩阵回归；
收益 = 一个本就不可防的威胁类里的边角。**判定不做**，改为把边界如实写进文档（已在 §1.4 与 SECURITY.md 口径内）。

### 丁 —— 运行期 .text / 关键序言周期自校验：判「本轮不做」

需要 `VirtualProtect`/`mprotect` 页管理与跨平台分叉，误杀面高（杀软、ASLR 补丁、Windows 更新改写），
而它能挡的是"已经拿到 shell 再补掉校验"——那条路 R6 已定性为"壳不受保护是设计边界"（SECURITY.md Tier B 表）。
**止于**：不进本波；若将来引入代码签名与 `self` 共存（契约 §6.5）再一并评估。

## 4. 对比表

| 方向 | 抬升哪条攻击路径的成本 | 破容器/清单格式 | 启动代价 | 改动面 | 失败模式 | 结论 |
|---|---|---|---|---|---|---|
| 甲 内存生命周期 | 内存 dump → 离线全量解密（缺口 1、2） | 否 | **−180ms**（PBKDF2 2→1） | 运行期 Go + 镜像 + Go/JS 测试 | 无 | **本波做** |
| 乙 多态装配 | 静态提取主密钥 + **跨产物复用**（缺口 3） | 否 | +数 ms（拼装） | CLI 注入面 + 生成模板 + 符号表测试 | 响亮拒跑（有长度校验兜底） | **本波做** |

## 5. 推荐与待裁

推荐：**甲 + 乙 同波实施**（互补：甲把"运行时取样"贬值，乙把"静态提取"成果贬值，二者共同把成本
推到"每个产物单独人工逆向"）。版本号与发布由用户裁（铁律 14），实施期不递增版本标识。

待裁（只有用户能答，且属架构取舍不是工程取舍）：
- **是否把"核心逻辑服务端化"列入路线**（§2.4：这是达成"逆向真拿不到源码"语义的唯一手段，代价是 freedom
  从"打包框架"扩到"客户端+服务端交付模型"）。建议：本波不动，作为独立评估波次；
  若用户要，我下一轮先出「最小可行：后端 RPC 出口 + 凭据托管」对比。
